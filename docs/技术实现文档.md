# 需求分析拆解智能体 — 技术实现文档

## 1. 概述

本智能体是"用例生成智能体"的上游环节，输入 Markdown 格式的 PRD，输出结构化测试点清单（JSON + Markdown），并附带校验报告与背景参考上下文，供下游用例生成环节消费。

### 1.1 处理流程

```
parse_md → classify_sections → detect_ambiguity → split_units → extract_points
→ validate ⇄ extract_points（未覆盖回灌，最多重试 N 轮）
→ human_review（interrupt 人工审核，可打回重抽）
→ output
```

### 1.2 技术选型

| 组件 | 选型 | 说明 |
| --- | --- | --- |
| 流程编排 | LangGraph 1.x | 状态图编排，原生支持 interrupt（人工节点）与 checkpointer（断点续跑） |
| LLM 调用 | OpenAI 兼容接口 | 通过 `base_url` 可切换任意兼容厂商，模型/密钥外置配置 |
| 文档解析 | 自研行级解析 | 不依赖第三方 MD 库，按标题文本切分章节（原因见 3.1） |
| 配置 | YAML | 章节词库与运行参数外置，模板变化改配置不改代码 |

## 2. 状态定义（src/state.py）

LangGraph 的 State 是贯穿全流程的数据总线，用 `TypedDict(total=False)` 定义，所有节点通过返回 dict 增量更新。

```python
class AgentState(TypedDict, total=False):
    prd_path: str                     # 输入：PRD 文件路径
    raw_md: str                       # 原文
    doc_title: str                    # 一级标题（文档标题）
    sections: List[Section]           # 全部章节（含分类标签）
    core_sections: List[Section]      # 核心需求章节（参与抽点）
    reference_sections: List[Section] # 背景参考章节（保留不抽点）
    removed_log: List[Dict]           # 去噪日志
    core_text: str                    # 核心需求文本（图片已替换占位符）
    reference_text: str               # 背景参考原文
    ambiguities: List[Dict]           # 歧义清单
    units: List[Unit]                 # 功能单元
    test_points: List[TestPoint]      # 测试点
    retry_hints: List[str]            # 校验/人工回灌给抽取节点的提示
    retry_unit_ids: List[str]         # 本轮需要补抽的功能单元；为空时全量补抽
    coverage_report: Dict             # 校验报告
    validate_retry: int               # 已重试轮数
    review_status: str                # approved / rejected
    human_feedback: str               # 人工批注
    next_route: str                   # 节点路由标记
    output_files: Dict[str, str]      # 产出文件路径
```

其中 `Section` / `Unit` / `TestPoint` 也是 TypedDict：

- `Section`：`id / heading / level / start_line / end_line / content / category(title|core|reference|noise)`
- `Unit`：`id / title / type / source`，type ∈ {触发规则, 频控, 交互, 数据填充, 状态流转, 实验分组, 其他}（仅作参考，不驱动检查单）
- `TestPoint`：`id / unit_id / title / origin`，origin ∈ {prd_explicit, derived}
  - `title`：一句话验证断言（前半句条件、后半句预期行为）
  - `origin`：`prd_explicit`=PRD 明确规则，`derived`=测试经验推导

> **测试点粒度为"覆盖清单"**：只保留"验证什么 + 从哪来"，前置数据、操作步骤、逐步预期、维度类型、溯源锚点一律下放下游用例展开环节。旧字段 `precondition/scenario/expected/type/source_lines` 已移除。

> **实现要点**：所有节点间传递的键必须先在 `AgentState` 中声明。LangGraph 1.x 会静默丢弃未声明的键（开发中 `_route` 未声明导致路由失败的坑即源于此），路由标记字段 `next_route` 因此显式声明。

## 3. 各节点实现细节

### 3.1 parse_md — MD 解析（nodes/preprocess.py）

**功能**：读取 PRD，切分章节，识别文档标题。

**为什么不依赖 heading 层级/第三方 AST 库**：实际 PRD 的标题层级不可靠——示例文档中 `## 衡量指标`、`## 需求描述` 带 4 空格缩进（标准 MD 里这是代码块而非标题），且子章节混用 `###`/`#####`。因此采用自研行级解析：

1. **标题识别**：正则 `^\s*(#{1,6})\s+(.*\S)\s*$`，允许任意前导空白，记录每个标题的 `行号 / 级别 / 文本`。
2. **章节范围切分**：每个标题的章节范围 = 从标题行到**下一个同级或更高级标题**之前。即标题 `## 需求描述` 会吞下其后所有 `###` 子章节（触发条件/频控/交互），直到下一个 `##` 或 `#`。
3. **文档标题**：第一个一级标题（`#`）作为 `doc_title`，类别标记为 `title`，不参与后续分类。

产出：`raw_md / sections / doc_title`。

### 3.2 classify_sections — 章节分类与去噪（nodes/preprocess.py）

**功能**：按词库把章节分为三类：核心需求（core）、背景参考（reference）、噪声（noise）。

**实现步骤**：

1. **直接匹配**：对每个章节标题文本做包含匹配（`keyword in heading`，不要求全等，容忍"需求描述（本期）"这类变体）。先匹配 core 词库再匹配 reference 词库。命中的章节打上 `direct` 标记。
2. **类别继承**：未直接命中的章节，找包含它的、已命中类别的最近祖先（嵌套层级最深的那个），继承其类别；无祖先命中则为 noise。包含关系判定：`A.level < B.level 且 A.start < B.start 且 A.end >= B.end`。
3. **拼接核心/参考文本**：只取**直接命中**的章节内容拼接成 `core_text` / `reference_text`。子章节内容已包含在父章节范围内，若把继承类别的子章节也拼进去会导致内容重复（开发中修复过的 bug）。
4. **块级预处理**：对 `core_text` 把图片语法 `![alt](url)` 替换为占位符 `[图片: alt]`；交互稿/设计稿/埋点等链接行保留原文（是否参与抽点由抽取 prompt 约束）。
5. **去噪日志**：只记录**顶层**噪声章节（父章节不是噪声的），避免父子重复记录。每条日志含 `章节名 / 行号范围 / 原因 / 前 200 字摘要`，写入最终报告供审计。

**词库配置**（config/sections.yaml）：

```yaml
core_keywords:        # 命中 → 参与抽点
  - 需求描述
reference_keywords:   # 命中 → 保留为背景参考，不抽点
  - 需求背景
```

规则：**除这两类外，其余章节一律去噪**（如衡量指标、埋点、附录）。

### 3.3 detect_ambiguity — 歧义检测（nodes/analyze.py）

**功能**：在抽点前暴露 PRD 中影响测试设计的歧义与缺失信息。

**实现**：单次 LLM 调用，输入 `core_text`（核心需求）+ `reference_text`（背景参考，帮助理解），输出 JSON 数组 `[{question, location, impact}]`。

**设计决策**（对应方案 b）：发现歧义**不打断流程**，清单随校验报告在人工审核节点一并展示。prompt 中约束"只列真正影响测试点设计的问题"，避免模型泛泛输出。

mock 模式返回空数组。

### 3.4 split_units — 功能单元切分（nodes/analyze.py）

**功能**：把核心需求切成原子功能单元，作为抽点和覆盖率统计的基本单位。

**实现**：单次 LLM 调用，输入 `core_text`，输出 `[{title, type, source}]`，程序侧补充 `id（U01 起）`。type 不在枚举内时归一为"其他"。

**prompt 关键约束**：

- 每个单元是可独立验证的最小规则块；
- **实验分组表必须独立成单元**，类型为"实验分组"；
- 埋点地址、外链、图片占位符不生成单元；
- 每个单元保留原文引用（`source` 字段），作为追溯锚点。

mock 模式降级为启发式切分：按 `##`~`######` 子标题各成一个单元（占位，仅供流程验证）。

### 3.5 extract_points — 测试点抽取（nodes/analyze.py)

**功能**：按功能单元逐个抽取**覆盖点级**测试点（不是用例）。

**实现**：

1. **逐单元调用 LLM**：每个单元一次调用，输入 = 单元信息 + `reference_text`（截断 2000 字，仅作理解上下文，prompt 明确"不要从背景抽点"），输出 `[{title, origin}]`。
2. **字段收敛**：`title` 为一句话验证断言（前半句条件、后半句预期行为）；`origin` 由模型标注（`prd_explicit` / `derived`），非法值归 `derived`。程序侧统一分配 `TP001` 起的连续 ID，按 `title` 去重。
3. **双模式（提示词承载）**：由 `test_point_mode` 选择系统提示词变体 `prompts.extract_points_system(mode)`：
   - `prd_focused`（默认）：只抽 PRD 明确规则 + 少量必要业务推导；通用异常、兼容性、并发、操作细节下放下游；
   - `extended`：允许较完整的测试经验扩展（更多异常/边界/状态/风险），不做数量限制；
   - 两模式共用同一字段契约与"不写操作步骤/测试数据"的底线约束；程序侧不对模式做额外硬性机制。
4. **粒度 few-shot**：prompt 内置"用例级反例 → 覆盖点级正例"对照（含等价分支合并示例），这是控制粒度的主要手段。
5. **extended 语义去重**：抽取完成后，一次 LLM 调用合并"换词不换意"的测试点（`DEDUP_*` prompt），失败时静默跳过；程序侧仍有 `title` 精确去重兜底。
6. **定向回灌重抽**：`retry_hints` 非空时，把遗漏规则句/人工意见 + 已有标题拼进 `retry_block`，要求只补不重复；`retry_unit_ids` 定位需补抽的单元，无可用目标时回退全量。完成后清空回灌状态。

### 3.6 validate — 完备性校验（nodes/validate.py)

**功能**：产出覆盖率报告（只统计 PRD 明确规则）与来源防伪；发现遗漏时回灌重抽。

**第零步：origin 防伪（纯规则，`_apply_origin_guard`）**

用 `split_rule_sentences` 得到的规则句集，对每个 `origin=prd_explicit` 的测试点按 `title` 做归一化包含匹配：匹配不到任何 PRD 规则句的**强制降级为 `derived`**，并记入 `origin_corrections`。保证"推导点不会冒充明确规则"，覆盖率不会被推导撑高。

**第一层：回映射覆盖校验（主）**

1. **原子规则句切分**（`split_rule_sentences`，纯规则）：把 `core_text` 逐行处理，剥离列表符（`- * ● | >`）和编号前缀（`1.` `1、`），跳过标题行、空行、分隔线，去重保序。
2. **过滤免测句**：正则跳过图片占位符（`^\[图片`）、地址行（`^\S*地址[:：]`）、纯 URL。
3. **LLM 逐句判定**：一次调用，输入规则句列表 + **仅 `prd_explicit` 的**测试点摘要（id/title），输出每句 `covered: true/false` 及未覆盖原因。程序侧统计 `prd_rules` 覆盖率 = covered / total。**`derived` 点不参与覆盖率**，只单独计数（`derived_points.count`）。

**第二层：交叉校验（按模式收敛）**

用同一抽取 prompt 对**全部单元整体**再抽一份测试点清单 B（独立于清单 A），LLM 结合功能单元列表对比 A/B，输出有效遗漏项。提示词按模式区分：

- `prd_focused`：**只允许补充 PRD 明确规则的遗漏**；属于"更细测试设计"（通用异常/兼容性/操作细节等）的差异一律不补；
- `extended`：可补推导点，但须能关联功能单元、语义不重复、非操作步骤。

只有 B 中相对 A 的有效遗漏会触发补抽，A 独有项只保留在报告中。mock 模式跳过。

> **原"第三层：单元×维度检查单"已移除**——其"每个单元凑齐维度"的要求与"不硬凑、以 PRD 规则为准"的粒度目标冲突。

**路由决策**：

```
uncovered ∪ cross_diff(from=B) 非空 且 validate_retry < max_retry（默认 1）
  → retry_hints = 未覆盖规则句 + B 差异项标题
  → retry_unit_ids = 按 Unit.source 包含关系 / B 差异项 unit_id 定位
  → 任一提示无法定位时回退为全部单元，否则回到 extract_points 定向补抽

否则 → human_review，并清空 retry_unit_ids
```

重试轮数存于 state 的 `validate_retry`，防止死循环。

### 3.7 human_review — 人工审核（nodes/deliver.py)

**功能**：LangGraph `interrupt` 节点，流程暂停等待人工决策；支持断点续跑。

**实现**：

1. 节点内调用 `interrupt(payload)`，payload 携带审核材料摘要：文档标题、测试点模式、单元数、测试点数、推导点数、覆盖率报告、歧义清单。
2. 图编译时挂 `InMemorySaver` checkpointer，interrupt 时状态落盘（内存），CLI 通过固定 `thread_id` 恢复。
3. **resume 协议**（CLI 与节点的约定）：
   - `{"status": "approved"}` → 置 `review_status`，路由到 output；
   - `{"status": "rejected", "feedback": "..."}` → 批注写入 `retry_hints`，并把 `retry_unit_ids` 设为全部单元，路由回 extract_points 按意见全量重抽，之后重新校验、重新进入人工审核。

### 3.8 output — 产出（nodes/deliver.py)

**功能**：审核通过后落盘三份文件，文件名基于文档标题（清洗 `\\/:*?"<>|【】` 等非法字符，截断 60 字）。

| 文件 | 内容 | 消费方 |
| --- | --- | --- |
| `{标题}_test_points.json` | 顶层 `mode`；`context.reference`（背景原文）、units、test_points（`id/unit_id/title/origin`）、coverage_report、ambiguities、removed_log、review | 下游用例生成智能体 |
| `{标题}_test_points.md` | 按单元分组的测试点表格（ID/覆盖断言/来源，来源区分 PRD / 推导） | 人工评审 |
| `{标题}_report.md` | 校验与审核报告：模式、测试点数（含推导点数）、PRD 规则覆盖率、未覆盖清单、交叉校验差异、来源降级记录、歧义清单、去噪日志、审核状态 | 人工评审/审计 |

`coverage_report` 结构（`{标题}_test_points.json` 内）：

```jsonc
{
  "mode": "prd_focused",
  "coverage": { "total": 42, "covered": 40, "coverage_rate": 0.952,
                "uncovered": [ { "sentence": "…", "reason": "…" } ] },   // 仅统计 prd_explicit
  "derived_points": { "count": 12 },       // 推导点单独计数，不进覆盖率
  "cross_check_diff": [ … ],
  "origin_corrections": [ … ]              // 标为明确规则但未匹配到规则句、被降级的记录
}
```

## 4. 图编排（src/graph.py）

```python
builder.add_edge(START, "parse_md")
... 线性边到 validate ...
builder.add_conditional_edges("validate", route_after,
    {"extract_points": "extract_points", "human_review": "human_review"})
builder.add_conditional_edges("human_review", route_after,
    {"extract_points": "extract_points", "output": "output"})
builder.add_edge("output", END)
graph = builder.compile(checkpointer=InMemorySaver())
```

- 两个条件分支共用一个路由函数 `route_after`：读 state 的 `next_route` 字段（由各节点返回时写入）。
- 配置文件路径作为 `build_graph` 参数传入，词库/模型配置在图构建期加载一次，通过闭包注入各节点。
- 测试点模式 `test_point_mode`（`build_graph` 参数，来自 `--test-point-mode` 或 settings）在图构建期解析，注入 `extract_points`/`validate`/`output` 节点；图对象上挂 `graph.test_point_mode` 供 CLI 展示。
- `graph.llm_mock` 标记挂在图对象上，供 CLI 提示当前是否 mock 模式。

## 5. LLM 封装（src/llm.py）

- **多 provider**：settings 中每个厂商一个顶层配置块，命名规则为 `llm`（默认块）或 `llm-<provider>`（如 `llm-deepseek`）。生效块优先级：命令行 `--llm-provider` > settings 的 `llm_provider` > `llm` 块。新增厂商只需加配置块，不改代码。
- **密钥解析优先级**：配置块内 `api_key` 直填 > `api_key_env` 指定的环境变量 > mock 模式。配置字符串支持 `${ENV_NAME}` 展开，推荐写 `api_key: "${DEEPSEEK_API_KEY}"`，让密钥只存在于环境变量。
- `LLMClient` 读 settings：模型名、base_url（空则取 `OPENAI_BASE_URL` 环境变量）、temperature。
- **temperature 约定**：不写或 `null` → 默认 0.2；显式写 `false` → **不向厂商传该参数**（部分模型温度固定，如 Kimi K3，传了会报错）。厂商特有参数（`max_tokens`、`top_p` 等）放在配置块的 `request` 映射下，原样透传。
- **mock 模式**：未检测到 API Key 且 `mock_when_no_api_key: true` 时，所有调用返回调用方传入的占位数据，保证流程无需真实模型即可端到端验证。
- `chat_json`：system 追加"只输出 JSON"，解析失败时用正则提取首个 JSON 数组/对象兜底，再失败抛异常。
- 所有 prompt 集中在 `src/prompts.py`，便于统一调优。
- 自检脚本：`python scripts/check_llm.py --llm-provider deepseek`，不进图、不触发人工审核，直接验证密钥与模型名是否被端点接受。

### 5.1 日志（src/logger.py）

- 日志同时输出到控制台和 `{log_dir}/agent.log`。控制台与文件均显式使用 UTF-8（`errors="replace"`）：Windows 默认 GBK 遇到 `\xa0`、生僻字会抛 `UnicodeEncodeError`，导致整条结构体日志丢失。
- **按节点命名 logger**：name 规则为 `prd_agent.<模块>`，节点日志为 `prd_agent.node.<节点名>`（如 `prd_agent.node.extract_points`），formatter 已含 `%(name)s`，因此多节点日志在同一文件里天然可区分。
- **入参/出参结构体打印**：`NodeLogger.start()` 打印节点入参（当前 state 全量结构体 + 顶层 keys），`end()` 打印出参（节点返回的增量 dict）与耗时。
- **截断预算**（配置项）：`log_max_chars` 单条结构体总长、`log_max_str_chars` 单字段长度（`raw_md`/`core_text` 靠它裁剪）、`log_max_items` 单列表项数；截断处标注 `…(+N chars/items)`，既保留结构形状又不会刷爆日志。
- 异常时先打印入参快照再打堆栈；`interrupt` 记为"暂停"而非异常。
- LLM 层记录初始化信息（provider / model / base_url / 掩码后的 api_key / mock）与每次请求的耗时、token 用量；不记录完整 prompt 与明文密钥。

## 6. CLI（main.py）

```bash
py -3 main.py <prd路径> [--thread-id TID] [--llm-provider deepseek]
               [--test-point-mode prd_focused|extended]
               [--sections-config ...] [--settings-config ...]
```

1. 构建图，`graph.invoke({"prd_path": ...}, config={"configurable": {"thread_id": ...}})`。
2. 返回含 `__interrupt__` → 打印审核材料（含测试点模式与推导点数）→ 读取人工输入：
   - `approve` → `Command(resume={"status": "approved"})`
   - `reject: <意见>` → `Command(resume={"status": "rejected", "feedback": ...})`
3. 循环直到无 interrupt，打印产出文件路径。
4. 启动时打印生效的 `provider`、`model` 与 `mode`，mock 模式额外给出提示。
5. Windows 控制台中文兼容：`sys.stdout.reconfigure(encoding="utf-8")`。

## 7. 配置说明

**config/settings.yaml**

```yaml
# provider 选择：对应下面的配置块（default → llm；deepseek → llm-deepseek）
# 也可用 --llm-provider 临时覆盖
llm_provider: deepseek

llm:                        # 默认块（Kimi Code K3）
  model: k3
  base_url: "https://api.kimi.com/coding/v1"
  api_key_env: MOONSHOT_API_KEY
  temperature: false        # 温度固定，客户端不传该参数

llm-deepseek:               # DeepSeek（OpenAI 兼容端点）
  model: deepseek-v4-flash
  base_url: "https://api.deepseek.com/v1"
  api_key_env: DEEPSEEK_API_KEY
  api_key: "${DEEPSEEK_API_KEY}"   # 直填密钥也可，但建议只放环境变量
  temperature: 0.2

mock_when_no_api_key: true  # 无 Key 时流程可跑通（占位产出）
validate_max_retry: 1       # 校验回灌重抽的最大轮数

# 测试点模式（可用 --test-point-mode 临时覆盖）
#   prd_focused  PRD 明确规则 + 少量必要业务推导；通用异常/兼容性/操作细节下放下游（默认）
#   extended     允许较完整的测试经验扩展（更多异常/边界/状态/风险），不做数量限制
test_point_mode: prd_focused

output_dir: output
log_level: INFO
log_dir: logs
log_max_chars: 4000       # 单条结构体日志的字符上限
log_max_str_chars: 300    # 单字段（长文本）字符上限
log_max_items: 20         # 单列表打印项数上限
log_node_level: INFO      # 节点日志级别
```

> 密钥安全：`config/settings.yaml` 已加入 `.gitignore`，禁止提交含明文密钥的配置。生产环境更推荐 `api_key: "${DEEPSEEK_API_KEY}"` + 环境变量注入。

## 8. 已知限制与后续优化方向

| 项 | 现状 | 优化方向 |
| --- | --- | --- |
| 图片/交互稿 | 保留为占位符，不做内容理解 | 引入多模态模型解析交互稿截图，补充 UI 细节测试点 |
| 歧义检测 | 只检测、汇总展示，不回填 | 人工确认歧义答案后作为补充上下文重跑抽点 |
| 章节分类 | 纯词库匹配 | 词库未命中核心章节时加 LLM 兜底判断 + 告警 |
| 交叉校验 | 整体重抽一次做 diff（按模式收敛补抽范围） | 独立 prompt 变体/不同温度多次抽样，投票 |
| 测试点粒度 | 覆盖点级（`title`+`origin`），操作细节/数据下放下游 | 与下游用例生成智能体确定最终边界；`prd_focused` 的"少量推导"目前纯靠提示词约束 |
| 推导点防伪 | `origin` 程序侧按规则句匹配降级 | 更精确的"业务蕴含"判定；推导点与规则的映射可视化 |
| checkpointer | 内存版（InMemorySaver），进程退出即失效 | 换 SqliteSaver/PostgresSaver 支持跨进程恢复审核 |
