## 2. 用例模板字段（禅道导入格式）

| 列 | 字段 | 规则 | 生成方式 |
| --- | --- | --- | --- |
| A | 所属模块 | 必填，模块路径，如 `/互动业务/消息详情/聊天区/自定义卡片/引导添加求职意向卡` | 模型根据功能单元生成 |
| B | 标题 | 必填 | 模型生成 |
| C | 前置条件 | 描述性文本 | 模型生成（含测试数据） |
| D | 步骤 | 按序号换行：`1. xxx\n2. xxx` | 模型生成 |
| E | 预期 | 与步骤按序号**一一对应**：`1. xxx\n2. xxx` | 模型生成 |
| F | 关键词 | 逗号分隔 | 模型生成 |
| G | 优先级 | 必填，1-4 | 用例设计环节定级（1 最高） |
| H | 用例类型 | feature/performance/config/install/security/interface/other | 默认 `feature` |
| I | 状态 | normal/blocked/investigate | 默认 `normal` |

模板示例文件：`import_template (1).xlsx`（注意：预期必须与步骤序号一一对应，导出前需程序校验）。

### 2.1 溯源字段（内部字段，不进禅道导入列）

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| source_type | new / reuse / update | 全新生成 / 直接复用历史用例 / 在历史用例上修改 |
| source_case_id | 禅道 case_id | source_type 为 reuse/update 时必填，用于后续同步禅道时定位原用例 |
| covered_point_ids | 测试点 ID 列表 | 覆盖追溯 |
| change_summary | 文本 | update 类型必填：相对历史用例改了什么、为什么改 |

**导出结构**：一个 xlsx 两个 sheet——
- Sheet1 `用例导入`：严格 9 列模板格式，保留模板第 1 行表头与第 2 行填写说明，数据从第 3 行开始（模板示例行不保留）；只含 new + update 类型（reuse 不入库，不出现）；
- Sheet2 `溯源明细`：标题、source_type、source_case_id、covered_point_ids、change_summary；
- 另有 JSON 留档含全量溯源字段，供程序消费。

## 3. 处理流程（LangGraph 子图）

```
load_input        读取上游 test_points.json（测试点/单元/背景参考/歧义确认结果）
    ↓
design_cases      用例设计（ReAct + 召回工具）：测试点聚类合并 → 用例骨架
                  （标题、覆盖测试点ID列表、优先级1-4、source_type 预判）
                  规则：同单元同链路的正向点合并；异常/反向/边界/频控单独成例
    ↓
generate_cases    按骨架逐条展开为步骤级用例（9 个模板字段 + 溯源字段全量生成）
                  背景参考上下文辅助生成业务合理数据；未确认歧义按假设生成并标注
                  上下文不足时可主动调用召回工具二次查找（见 3.1）
    ↓
validate_cases    三层校验：
                  ① 格式校验（纯规则）：必填字段非空、步骤与预期序号一一对应、
                     优先级∈1-4、类型/状态在枚举内
                  ② 覆盖回映射：每条测试点 ≥1 条用例覆盖（source_type=reuse 视为已覆盖），
                     未覆盖回灌重生成（限重试轮数）
                  ③ 质量审查（LLM）：步骤可执行性、预期可断言、数据自洽；
                     含 source_type 终判——与历史用例比对，纠正生成阶段的预判
                     （new 实际已存在→update/reuse；update 实际无对应历史→new）
    ↓
human_review      interrupt 人工审核（approve / reject: 意见，与上游同一交互）
    ↓
export_excel      导出 xlsx（双 sheet：用例导入 + 溯源明细）+ JSON 留档
```

### 3.1 生成中的二次查找（Agent 主动召回）

召回不做一次性固定节点，而是把 RecallService 封装成**只读工具集**，注入 design_cases / generate_cases（LangGraph `create_react_agent` 承载），模型判断上下文不足时主动再查：

| 工具 | 作用 |
| --- | --- |
| `search_cases_by_module(module_path)` | 按模块召回历史用例，返回完整字段（初始召回也走它） |
| `search_cases_by_keyword(query)` | 模块内/跨模块关键词查找，返回完整字段 |
| `list_modules()` | 查看禅道模块树（供模块对齐选择） |

> 决策：不设 `get_case_detail` 工具——搜索工具直接返回用例完整字段（标题/前置/步骤/预期），无需二次取详情。
> 上下文保护（分页模式）：搜索工具按页返回，默认每页 2 条（page_size 可配置），返回结构为
> `{cases: [...], page, page_size, total, total_pages}`，模型需要更多时带 `page` 参数再次调用翻页。

护栏：限制最大工具调用轮数（默认 15，需覆盖翻页场景），防止死循环与 token 失控；工具全部只读，不写业务库。
本期 RecallService 为接口 + 空实现，工具存在但返回空，主链路不受影响；接入禅道数据后无需改流程。

## 6. 历史用例召回方案

### 6.1 时机：两处插入，缺一不可

- **召回点 ①（用例设计之前）**：功能单元归属模块确定后，召回对应模块的历史用例，作为生成的**风格/粒度参考**，同时作为复用判定的候选集。
- **召回点 ②（生成之后、人工审核之前）**：新生成用例与历史用例做相似比对，逐条标注关系：**复用**（历史已覆盖，不再重复入库）/ **更新**（历史用例存在但预期已过时，给出修改建议）/ **新增**。审核人看到的是带标注的清单，而不是一堆可能重复的用例。

### 6.2 数据架构（已确认）

**不做向量召回**。用例生成场景的召回目标是明确的——改动模块下的历史用例，模块匹配足够：

```
禅道（用例源头）
  → 业务数据库（SQL）：用例本体 + 模块关联 + vector_id
  → 向量数据库：用例向量（标题+前置+步骤+预期），metadata 回存 case_id / 模块路径
```

- 用例生成智能体：**直接从业务库按模块匹配召回历史用例**，不经过向量库；业务库记录中带有向量库索引（vector_id），需要时可反查。
- 向量数据库定位：服务于后续业务智能体（业务问答等）；对用例生成智能体的潜在价值见 6.4。

### 6.3 召回方式与前置依赖

1. **模块过滤（唯一一级）**：按模块路径从业务库取出该模块历史用例。模块下用例量大时，在模块内按功能单元关键词做轻量过滤/分批，控制送入 LLM 的规模。
2. **前置依赖——模块对齐**：模块路径若由模型自由生成，会与禅道实际模块树对不上导致召回失效。因此"模块从禅道读取"是召回的**硬前置**：生成时把禅道模块树注入 prompt，让模型从现有模块中**选择**而非自由生成，无合适模块时才新建。
3. **复用判定**：召回的历史用例交 LLM 判定关系：复用 / 更新 / 新增。

### 6.4 向量库对用例智能体的潜在价值（后续迭代再评估）

- 跨模块相似用例发现与去重（模块匹配覆盖不到的场景）；
- PRD 变更影响面分析：需求描述向量 vs 全量用例向量，定位改动模块外的受影响历史用例。

### 6.4.1 关于"关联模块字段"的讨论结论（已确认暂不做）

曾评估在业务库新增 AI 生成的"关联模块"字段、按 模块+关联模块+RAG 三路召回。结论：**与向量召回功能重叠度高，暂不做**——关联模块字段本质是用结构化字段预计算向量召回能自动发现的关系，且存在存量回填、双向一致性、随业务演化腐化等维护成本。
例外场景：向量召回解决"语义相似"，解决不了"业务依赖"（如埋点模块与前端卡片模块文本不相似但强依赖）。若后续做变更影响面分析，可再引入该字段，但语义应定义为"依赖"，且优先从历史变更数据挖掘或人工维护关键依赖，而非 AI 逐条自由生成。

### 6.5 数据一致性要求

- 同步链路：禅道 → 业务库 → 向量库，全量初始化 + 增量同步（webhook 或定时轮询）；**用例删除也要同步向量库**（最易遗漏）。
- 关联键：禅道 case_id 为主键，业务库存 vector_id；向量库 metadata 存 case_id、模块路径、内容 hash（判断字段变更后是否需要重新 embedding）。
- **回流闭环**：审核通过并导入禅道的新用例，需回写业务库 + 向量库，否则两个库逐渐与真实用例库漂移。

### 6.6 落地节奏

- 本期：用例生成主链路（召回层抽象为 `RecallService` 接口，模块匹配版后续实现，接口不变）；
- 下一迭代：禅道模块树对齐 + 业务库模块匹配召回 + 复用判定；
- 向量库建设跟随业务问答智能体的排期。

## 7. 备选方案留档

若"正向合并、异常独立"的生成效果不佳（如合并后步骤过长、覆盖关系模糊），切换为**测试点与用例严格一对一**：design_cases 环节退化为直接映射（一个测试点一条用例骨架），其余流程不变。切换成本低，只需替换 design_cases 节点实现。
